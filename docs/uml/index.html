ScheduNova UML Diagrams

ScheduNova is an AI personal scheduling assistant. A user types or speaks a task in plain language ("Gym tomorrow 7am for an hour, high priority"), the system turns it into a structured task, and plans the user's day around priorities, durations, fixed start times and deadlines. The backend is a Frappe 16 app backed by MariaDB, with Google Gemini doing the language parsing.

Implemented in code

Sign-up, login and CSRF API (api.py), the Nova Task DocType with its fields and duration check, per-owner permissions, and the bench services.

Planned (shown as «planned»)

Gemini task parser and day planner. The Gemini key is already in the site configuration, but neither component is in the code yet.

Entities, their fields and how they relate

The attributes of NovaTask come straight from nova_task.json, including the defaults. User and Document are Frappe framework classes that the app builds on.

  NovaTask --> Priority
  User "1" --> "0..*" NovaTask : owns
  SchedunovaAPI ..> User : creates
  TaskParser ..> NovaTask : creates
  DayPlanner ..> DayPlan : creates
  DayPlan "1" *-- "1..*" TimeBlock : composition
  TimeBlock "0..*" o-- "1" NovaTask : aggregation
  DayPlan "0..*" --> "1" User : for
  • Generalization: User and NovaTask both inherit from Frappe's Document, which supplies name, owner, timestamps and the insert, save and validate lifecycle. NovaTask overrides validate() to reject duration_min ≤ 0.
  • Association: one user owns many tasks through the standard owner field. Task names are random hashes (autoname: hash).
  • Composition: a DayPlan is made of its TimeBlocks, and the blocks are deleted with the plan. Aggregation: a block points to a NovaTask that exists independently of it.
  • raw stores the user's original sentence. It is read-only, so only the server sets it. Planned: TaskParser, DayPlanner, DayPlan and TimeBlock.

Sequence diagrams

Two critical scenarios: signing up, and adding a task by sentence

Scenario A follows schedunova.api.sign_up line by line, including the rate limit and the duplicate-email check. Scenario B is the main AI feature. Its parse step is planned, but the save and validation steps are real.

sequenceDiagram
  autonumber
  actor G as Guest
  participant FE as ScheduNova Web UI
  participant FS as Frappe server
  participant RL as Rate limiter
  participant DB as MariaDB
  G->>FE: Enter name, email, password
  FE->>FS: POST /api/method/schedunova.api.sign_up
  FS->>RL: apply(limit=5, seconds=3600)
  alt more than 5 attempts in the last hour
    RL-->>FE: 429 Too Many Requests
  else within limit
    FS->>FS: Normalise email, validate_email_address()
    FS->>DB: exists("User", email)?
    alt email already registered
      FS-->>FE: Error "An account with this email already exists"
    else new email
      FS->>DB: INSERT User (Website User, enabled)
      FS->>DB: update_password(user, password)
      Note over FS,DB: Weak password throws and the whole request rolls back
      FS-->>FE: {ok: true, user: email}
      FE->>FS: POST /api/method/login (usr, pwd)
      FS-->>FE: Set-Cookie sid (session)
      FE->>FS: GET schedunova.api.get_csrf_token
      FS-->>FE: {csrf_token}
      FE-->>G: Show task dashboard
    end
  end

Scenario B: add a task from a natural-language sentence.

The flow of adding a task, from first input to saved record

This diagram covers both input paths (sentence and form), the fallback when parsing fails, the validation loop, and the concurrent work done after a save.

  OK -- Yes --> RV["Show parsed fields for review"]

  CH -- No --> V
  FB --> FRM
  M -- Fill a form --> FRM
  FRM --> V{"Title set and duration_min > 0?"}
  V -- No --> ER["Show validation error"] --> FRM
  V -- Yes --> SV["Save Nova Task"]
  SV --> F1[" "]:::bar
  F1 --> LS["Refresh task list"]
  F1 --> PL["Recompute day plan (planned)"]:::planned
  LS --> J1[" "]:::bar

  J1 --> E((End)):::term
  classDef bar fill:#17212B,stroke:#17212B
  classDef term fill:#17212B,stroke:#17212B,color:#FFFFFF

  • Diamonds are decisions, and every branch is labelled with its guard. The two black bars are the fork and join: the list refresh and plan recompute run in parallel.
  • A failed parse never loses the user's input. The sentence is kept in raw and the user finishes the task by hand.
  • The validation loop mirrors the server: title is reqd in the DocType, and validate() rejects a non-positive duration.
PlantUML source (standard UML notation) 
@startuml
start
if (Logged in?) then (no)
  :Log in or sign up;
endif
if (How will the task be added?) then (type or speak)
  :Send sentence to server;
  :Gemini parses task fields;
  if (Parse succeeded?) then (yes)
    :Show parsed fields for review;
    if (User wants changes?) then (yes)
      :Edit fields in form;
    endif
  else (no)
    :Open form, keep raw sentence;
    :Edit fields in form;
  endif
else (fill a form)
  :Edit fields in form;
endif
while (Title set and duration_min > 0?) is (no)
  :Show validation error;
  :Edit fields in form;
endwhile (yes)
:Save Nova Task;
fork
  :Refresh task list;
fork again
  :Recompute day plan (planned);
end fork
stop

State machine diagram

The life of a single Nova Task

The database stores only done, fixed_start and deadline. States such as Scheduled and Overdue are derived from those fields at read time, so this diagram shows how the app treats a task, not extra columns.

%%{init: {"theme": "neutral"}}%%
stateDiagram-v2
  [*] --> Draft : sentence parsed or form opened
  Draft --> [*] : cancel
  Draft --> Open : save [validate passes]
  state Open {
    [*] --> Pending
    Pending --> Scheduled : fixed_start set
    Scheduled --> Pending : fixed_start cleared
    Pending --> Overdue : [now > deadline]
    Scheduled --> Overdue : [now > deadline]
  }
  Open --> Done : tick Done / done = 1
  Done --> Open : untick Done / done = 0
  Open --> Deleted : delete
  Done --> Deleted : delete
  Deleted --> [*]
  • Open is a composite state. Ticking Done from any of its substates leaves it, and unticking re-enters at Pending.
  • Labels read event [guard] / action. For example, save [validate passes] means the save only succeeds when duration_min is positive.
  • Draft exists only in the UI, before the first save. track_changes = 1 on the DocType records every later transition in the version log.

Modules of the system and what depends on what

The schedunova app is a thin layer on top of Frappe. It adds an API module and one DocType, and it reuses the framework's REST layer, authentication, permissions and ORM.
